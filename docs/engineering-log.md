# 工程改进记录

用于记录有学习和简历表达价值的 Bug 修复、性能优化与架构调整。

## 2026-08-07｜实时检测流水线与并发队列重构

### 1. 统一管理实时处理流程

- 原先表现：`main()` 同时负责拉流、推理、画框、编码和推流，启动顺序分散，后续增加停止、重连和错误处理会越来越复杂。
- 为什么改：流程没有统一负责人，各模块的生命周期不清晰，错误发生后难以集中处理。
- 具体做法：新增 `VideoAnalyticsPipeline`，集中管理配置、媒体缓存、推理线程池及工作线程；入口程序只解析参数并启动 Pipeline。
- 改进效果：主流程更加清晰，后续可以在 Pipeline 中统一加入断线重连、状态管理和资源回收。当前需在 RK3588 开发板上完成运行验证。

### 2. 用阻塞队列替代循环查询

- 原先表现：队列为空时，线程每隔几毫秒醒来检查一次；既产生无效唤醒，也可能增加取帧延迟。
- 为什么改：循环 `sleep` 属于轮询等待，线程没有数据时仍会反复运行，而且程序停止时不容易唤醒等待线程。
- 具体做法：实现带互斥锁和条件变量的 `FrameQueue`。放入帧后立即通知消费者；队列关闭时唤醒所有等待线程。
- 改进效果：没有数据时线程会真正休眠，新帧到达后可立即唤醒；退出流程也有明确通知机制。CPU 和延迟改善待开发板实测。

### 3. 限制视频帧缓存长度

- 原先表现：处理速度低于输入速度时，视频帧可能持续积压，造成内存增长和画面延迟。
- 为什么改：实时监控更关注最新画面，长期处理旧帧会让结果失去实时性。
- 具体做法：为帧队列设置容量，默认保留 10 帧；超过容量时丢弃最旧帧。
- 改进效果：缓存占用有上限，系统过载时优先保持较新的画面，代价是高负载下可能丢帧。

### 4. 修复线程池共享容器的数据竞争

- 原先表现：一个线程在检查任务数量或查找结果时，另一个线程可能同时修改同一个 `queue/map`，运行结果不稳定。
- 为什么改：C++ 标准容器不支持无锁的并发读写，可能出现偶发崩溃、错误结果或难以复现的问题。
- 具体做法：任务队列和结果表分别使用互斥锁保护；使用条件变量等待“有任务”“有空位”和“有结果”；停止状态改为原子变量。
- 改进效果：共享数据的读写顺序明确，消除了已识别的数据竞争和忙等待。仍需结合开发板压力测试确认长期稳定性。

### 5. 分离推理和画框职责

- 原先表现：推理线程池内部直接绘制检测框，检测结果难以复用于告警、截图、统计或 JSON 上报。
- 为什么改：线程池应该只负责计算，结果如何使用应由业务层决定，否则每增加一种业务都要修改推理模块。
- 具体做法：新增 `InferenceResult`，统一返回帧 ID、图像和检测结果；画框移动到 Pipeline 的结果处理阶段。
- 改进效果：同一份检测结果可以继续扩展画框、告警、保存和上报逻辑，而不需要修改 YOLO 推理线程池。

### 当前限制

- MPP 解码、编码代码仍通过兼容接口绑定当前 `MediaBuffer`，尚不能安全地同时运行多路 Pipeline。
- 当前 Windows 环境缺少 CMake 和目标平台工具链；以上改动已完成静态检查，编译和性能数据待 RK3588 开发板验证。

## 2026-08-08｜增加 PC 端 YOLOv5 流程测试

- 原先表现：YOLO 检测代码只能依赖 RKNN 在 RK3588 上运行，没有开发板时无法快速检查输入、推理、画框和结果输出流程。
- 为什么改：开发早期的大部分流程问题不需要在板端排查；PC 上先验证可以缩短调试周期，并区分通用流程问题和 RK3588 平台问题。
- 具体做法：新增独立的 `pc_yolov5` 可选目标，使用 OpenCV DNN 加载 YOLOv5 ONNX，支持图片、视频和 PC 摄像头输入，并保存画框结果；CMake 可关闭全部 RK3588 目标，只构建 PC Demo。
- 改进效果：预期可在 PC 上验证完整的基础检测流程，同时不影响原有 RKNN/MPP 构建。当前环境缺少 CMake、OpenCV PC 开发包和 ONNX 测试模型，编译及检测结果待本机依赖准备完成后验证。

## 2026-08-08｜梳理项目结构和构建分组

- 原先表现：`CMakeLists.txt` 中重复列出媒体源文件和平台库，README 对源码分层的说明较粗，后续新增目标或移动目录时容易漏改。
- 为什么改：当前工程已经分出推理、媒体、Pipeline、PC Demo 等模块，但结构意图主要藏在文件名和 include 路径里，协作和扩展成本会逐渐升高。
- 具体做法：在 CMake 中增加源文件清单、公共 include 清单和平台库清单，减少重复目标配置；将各示例入口迁入 `apps/`，将 YOLOv5 模型封装和线程池迁入 `src/yolov5/`，将标签、测试素材和 RKNN 模型迁入 `assets/`；新增 `docs/project-structure.md` 记录当前结构和后续迁移顺序，并同步 README。
- 改进效果：入口、模型代码、媒体代码和运行资源的边界更清楚，`src` 不再混放 demo main 文件。当前 Windows 环境缺少 CMake，编译验证仍需在具备依赖的 PC 或 RK3588 开发板上完成。
