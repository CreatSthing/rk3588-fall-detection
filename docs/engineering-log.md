# 工程改进记录

只记录当前 RK3588 智能跌倒检测项目中有验证价值的修复与优化。

## 2026-08-17｜建立姿态跌倒检测与录像闭环

- 原先表现：系统只有普通目标框和手动录像，无法判断跌倒或保存事件。
- 为什么改：单帧躺卧不等于跌倒，告警后才录像也会丢失事发前画面。
- 具体做法：接入 YOLOv8n-Pose RKNN、多人跟踪和“快速下落 + 水平姿态 + 持续确认”规则；缓存事发前5秒和后10秒画面；用 SQLite、WebSocket 和 MP4 串起事件闭环。
- 改进效果：272帧公开跌倒视频中271个有人帧保持同一跟踪 ID，触发一次真实告警并生成可下载录像。

## 2026-08-17｜补齐骨架与7类动作

- 原先表现：前端只画人员框，算法只输出正常、疑似和跌倒。
- 为什么改：缺少关键点和中间动作会使现场调参与误报分析缺少依据。
- 具体做法：前端绘制 COCO 17点骨架；增加站立、行走、坐姿、躺卧、起身、落座和跌倒状态；跟踪增加归一化中心距离，本地视频使用帧时间轴。
- 改进效果：离线跌倒回放可以连续显示人体骨架、动作变化、跟踪 ID 与最终告警；起身和落座分支由单元测试覆盖。

## 2026-08-17｜修复骨架与画面错位

- 原先表现：视频与骨架来自两条不同延迟的链路，骨架不能稳定贴合人体。
- 为什么改：独立 WebRTC 播放与 RTSP 推理的时间点和缩放不同，无法保证同帧。
- 具体做法：从事件环形缓存取 JPEG，并与同一 `frame_id` 的检测结果成对通过 WebSocket 发送；前端在图片解码后原子更新画面和 SVG。
- 改进效果：板端捕获的640×360 JPEG、人员框和17个关键点属于同一帧，浏览器自动化检查确认可见关键点位于人体框内。

## 2026-08-17｜修复实时画面持续落后

- 原先表现：输入帧率高于推理帧率时，浏览器画面会不断积压并落后数分钟。
- 为什么改：FFmpeg stdout 是 FIFO，逐帧处理会无限排队旧帧。
- 具体做法：网络流使用独立取帧线程持续排空，只向推理保留最新完整帧；本地视频仍逐帧读取，事件录像按真实采样时间计算帧率。
- 改进效果：过载时主动丢弃旧源帧，实时延迟保持有界，离线验证仍不跳帧。

## 2026-08-17｜收口板端运行兼容性

- 原先表现：模型、RKNNLite 和 Runtime 版本混用会加载失败；自动硬解出现 RGA 步长错误；OpenCV 无法可靠写出 MP4。
- 为什么改：三类问题来自不同层，任何一项都会阻断告警录像链路。
- 具体做法：统一 Toolkit、RKNNLite 和 Runtime 到2.3.2；网络流显式使用 FFmpeg 软件解码，事件录像使用 FFmpeg/libx264；增加模型清单、验收脚本和 systemd 服务。
- 改进效果：非 root 服务可自动拉起摄像头和 NPU 管线，连续出帧无 RGA 错误，告警可推送、确认、重启保留并下载录像。

## 2026-08-17｜支持浏览器修改摄像头并自动重连

- 原先表现：热点网段变化后，只能登录开发板手工改 RTSP 地址。
- 为什么改：DHCP 地址可能变化，手工编辑容易覆盖其他运行配置。
- 具体做法：在摄像头卡片加入连接表单；更新时只修改浏览器管理字段，保留检测命令和自启设置；保存后重启转推，等内部 RTSP 可读再启动检测。
- 改进效果：Web 更新请求已在板端验证，配置、转推和检测会自动重连，无需 SSH。

## 2026-08-18｜完善告警管理和可调阈值

- 原先表现：告警无法删除，声音通知只能开不能关，触发置信度只能修改代码。
- 为什么改：长期运行需要清理误报，不同机位也需要独立调整灵敏度。
- 具体做法：增加安全删除 API；通知开关持久化；阈值写入板端配置，同时传入检测进程并由 Web 后端二次校验。
- 改进效果：页面可调整阈值、开关通知并删除完成事件；阈值边界、数据库和录像联动均已在板端验证。

## 2026-08-18｜修复录像残留状态与资源监控口径

- 原先表现：服务在录像期间中断后会永久显示“录像生成中”；NPU 误显示100%，单核 NPU 和 RGA Scheduler 为空。
- 为什么改：残留状态阻止事件删除，调频频率也不能代表真实 NPU 负载。
- 具体做法：启动时用 ffprobe 收敛残留录像状态；NPU 只读取 `rknpu/load` 的 Core0/1/2，RGA 读取 `rkrga/load` 的三个 Scheduler，读取失败时明确显示不可用。
- 改进效果：未完成录像数收敛为0；页面显示真实 NPU 三核和 RGA Scheduler 瞬时负载。

## 2026-08-18｜实现手动录像与阶段耗时可视化

- 原先表现：未配置自定义命令时，录像按钮只变状态不生成文件；总 FPS 不能说明阻塞阶段。
- 为什么改：假录像会误导用户，性能调优需要区分取帧、预处理、NPU 和后处理。
- 具体做法：后端用 FFmpeg 直接封装内部 RTSP 为 MP4；增加录像列表、播放和下载；检测结果输出阶段指数平滑耗时。
- 改进效果：板端6秒操作生成5.25秒有效 MP4；阶段数据定位当时主要瓶颈为单上下文 FP16 NPU 推理。

## 2026-08-18｜重新校准 YOLOv8-Pose INT8

- 原先表现：初版 INT8 用40张几乎无人的画面校准，人体置信度固定为0.500，只能回退 FP16，实时约11 FPS。
- 为什么改：空场景无法覆盖人体检测头和关键点分支的激活范围。
- 具体做法：从本地跌倒/起身视频抽帧，混入 COCO128 和 COCO8-Pose 人体及负样本，形成126张去重校准集；使用 Rockchip 官方混合量化配置，并以未参与校准的图片和视频对照 FP16。
- 改进效果：独立图片两模型均检出30/30，跌倒视频均检出271/272帧；INT8 NPU耗时由72.1 ms降到32.7 ms，端到端由11.13提升到20.65 FPS，且不再出现固定0.500置信度。

## 2026-08-18｜移除旧目标检测工程并收敛仓库

- 原先表现：仓库混有另一个项目的 C++ 目标检测源码、第三方 SDK、构建脚本、模型、服务和文档，README 也同时描述两套主链路。
- 为什么改：无关代码扩大仓库体积和维护面，还会让部署人员误用旧模型或旧服务。
- 具体做法：删除旧 C++ 工程及其专用资产、工具、部署文件和文档；清理后端兼容分支；重写 README 和项目结构说明；安装与验收脚本统一检查当前 INT8 姿态模型。
- 改进效果：仓库只保留 Python YOLOv8-Pose 跌倒检测链路，目录边界、默认模型和部署说明与当前板端一致；Python 测试结果见本次变更验证记录。
